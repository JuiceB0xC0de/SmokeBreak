# base16384

**TLDR;** Encodes any binary file as dense CJK characters in UTF-16BE, a base64 alternative that turns bytes into text that looks like Chinese.

base16384 reads a file or stdin and writes printable text drawn from 16384 characters, U+4E00 to U+8DFF. It works like base64, but the alphabet is 16384 symbols instead of 64. Each character carries 14 bits of input, so the output is shorter than base64 and reads as a block of Chinese-looking glyphs. Decoding turns the text back into the original bytes.

The README gives two reasons for the design. It saves more space than base64. And since the code 0x0000 encodes to "一", zero-filled regions in a binary are easier to spot in the encoded text. In the README's words: "Save more space and since the code 0x0000 is encoded to "一", finding zero space seems to be easier."

The idea underneath is that an encoding is just a choice of alphabet and bit width. Base64 packs 6 bits per symbol, and here 14 bits per symbol land in a Unicode range. Input that is not a multiple of 7 bytes gets a trailing marker of the form \u3Dxx, with xx from 01 to 06, recording the leftover bytes. Output starts with a UTF-16BE byte order mark unless you pass -n, and -c or -C adds or checks a checksum.

Because the output is UTF-16BE rather than UTF-8, a terminal will not show it directly. The README's examples pipe through iconv to convert in each direction.

## Install

```
brew install base16384
# Debian Bookworm or newer: sudo apt install base16384
# Arch AUR: yay -S base16384
```

## Try this

```
echo -n "1234567" | base16384 -e - - | iconv -f utf-16be -t utf-8
```
Encodes seven bytes from stdin and prints them as the four CJK characters 婌焳廔蠷 after iconv converts them for display.

```
echo -n "婌焳廔蠷" | iconv -f utf-8 -t utf-16be | base16384 -d - -
```
Converts the CJK string to UTF-16BE and decodes it back to 1234567.

```
base16384 --help
```
Prints the usage synopsis: -e, -d, -t, -n, -c, -C, and - for stdin or stdout.

## What's unique

It trades base64's ASCII alphabet for 16384 CJK characters at 14 bits each, so encoded data is a compact block of Chinese-looking text. Zero bytes show up as repeated "一".

## Caveats

The output is UTF-16BE, not ordinary text, so it needs the matching decoder or an iconv step, and the README gives no clear release or maintenance dates.
